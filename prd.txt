# మా పని పుస్తకం

## Digital Telugu Work Notebook for Masons & Small Contractors

**PRD Version:** 2.0
**Status:** Build Specification
**Target:** Production / Play Store quality
**Primary Platform:** Android
**Primary User:** Telugu-speaking mason / small construction contractor
**Primary UX:** Digital physical notebook
**Primary Requirement:** Extremely simple, reliable, elderly-friendly
**Connectivity:** Offline-first
**Distribution:** Google Play + GitHub APK distribution
**Development Environment:** Antigravity

---

# 1. PRODUCT DEFINITION

## One-sentence definition

**“మేస్త్రీ రోజూ పుస్తకంలో రాసుకునే పని లెక్కల పుస్తకాన్ని, అదే సహజమైన Telugu అనుభూతితో ఫోన్‌లోకి తీసుకురావడం.”**

The application is NOT:

* accounting software
* ERP
* payroll software
* CRM
* inventory system
* project management software
* invoicing software

It is a:

# Digital Work Notebook

The user thinks in:

**పని → రోజు → వచ్చిన డబ్బు → కూలీల డబ్బు → ఇతర ఖర్చు → మిగిలింది**

The application must think in the same structure.

---

# 2. PRODUCT NORTH STAR

The application succeeds if the father can use it and say:

> **“పుస్తకంలో ఎలా రాస్తానో అలాగే ఇక్కడ రాస్తున్నా. లెక్క మాత్రం ఫోన్ చూసుకుంటుంది.”**

It fails if he says:

> **“ఏది ఎక్కడ నొక్కాలో అర్థం కావడం లేదు.”**

Technical sophistication is irrelevant if the second statement happens.

---

# 3. TECH STACK

## Recommended Stack

### Android

**Kotlin**

Primary programming language.

Reason:

* first-class Android support
* strong type safety
* excellent coroutine support
* mature ecosystem
* long-term maintainability

---

## UI

### Jetpack Compose

Use Compose as the complete UI layer.

Benefits:

* modern Android UI architecture
* easy custom notebook UI
* easier state-driven screens
* custom animations
* reusable design system

Compose is actively maintained in the AndroidX ecosystem.

---

# 4. ARCHITECTURE

Use:

# Clean Architecture + MVVM

Layers:

```text
UI
↓
ViewModel
↓
Use Cases / Domain
↓
Repositories
↓
Room Database
```

Never put business calculations directly inside UI composables.

---

# 5. DATABASE

## Room + SQLite

Use Room as the local database layer.

Room provides an abstraction over SQLite and is appropriate for structured local application data.

The database is the application's:

# Single Source of Truth

UI state must not become the permanent source of financial information.

---

# 6. REACTIVE DATA

Use:

**Kotlin Coroutines + Flow**

for database observation and UI state updates.

Example:

When a ₹500 expense is added:

Database changes
↓
Repository emits update
↓
ViewModel receives update
↓
Summary recalculates
↓
UI updates

No manual refresh button should be necessary.

---

# 7. DEPENDENCY INJECTION

Use:

**Hilt**

for:

* database
* repositories
* use cases
* ViewModels
* update manager
* backup manager

Avoid manually constructing large dependency graphs.

---

# 8. NAVIGATION

Use:

**Jetpack Navigation Compose**

Navigation should preserve:

* current work
* current date
* current screen
* unsaved-state handling

Back navigation must never unexpectedly lose data.

---

# 9. LOCAL STORAGE

Use Room for structured data.

Use Android app-private storage for:

* backup files
* temporary exports
* update metadata
* generated reports

Do not store financial records in random JSON files as the primary database.

---

# 10. MONEY REPRESENTATION

This is critical.

Never store money as floating-point values.

Use an integer representation of the smallest supported currency unit.

For example:

₹500 → internal integer representation.

This prevents floating-point calculation errors.

Display using Indian formatting:

₹1,000
₹10,000
₹1,00,000
₹10,00,000

---

# 11. DATE/TIME

Store transaction dates using a reliable date representation.

Do not rely on formatted strings for sorting.

Store:

* transaction date
* created timestamp
* updated timestamp

The displayed date should be:

**13 సెప్టెంబర్ 2026**

not:

**2026-09-13**

---

# 12. TIMEZONE

Use the device's local timezone for user-facing dates.

A transaction entered on September 13 must not suddenly appear under September 12 because of UTC conversion.

Internally store timestamps safely.

Display dates according to the device's current local timezone.

# 20. CORE CALCULATIONS

For each Work:

### Total received

Sum of all valid income records.

### Labour total

Sum of all labour payment records.

### Other expense total

Sum of all expense records.

### Total expense

```text
labour + other expenses
```

### Remaining

```text
income - total expense
```

Display:

**వచ్చింది**

**కూలీలకు**

**ఇతర ఖర్చు**

**మొత్తం ఖర్చు**

**మిగిలింది**

---

# 21. IMPORTANT ACCOUNTING TERMINOLOGY RULE

Never label:

**మిగిలింది**

as:

**Profit**

because the application does not know:

* contract value
* unpaid work
* owner's outstanding amount
* business overhead
* personal withdrawals
* taxes
* depreciation
* other costs

The application only knows recorded money.

Therefore:

# “మిగిలింది”

is correct.

**“దాచాం”**

---

# 62. APP KILL EDGE CASE

Scenario:

User saves ₹5,000.

Immediately:

* app is killed
* phone restarts
* battery dies

After reopening:

₹5,000 must still exist.

---

# 63. DOUBLE TAP EDGE CASE

User rapidly taps:

**దాచు**

10 times.

System must not create 10 duplicate entries.

The save operation must be protected against duplicate submission from the same UI action.

---

# 64. BACK BUTTON EDGE CASE

---

# 65. ROTATION / CONFIGURATION CHANGE

The application must not lose partially entered information during:

* rotation
* activity recreation
* system memory pressure

Use proper ViewModel/state restoration mechanisms.

---

# 66. LOW STORAGE

If device storage becomes critically low:

Show:

**“ఫోన్‌లో ఖాళీ స్థలం చాలా తక్కువగా ఉంది. కొంచెం స్థలం ఖాళీ చేసి మళ్లీ ప్రయత్నించండి.”**

---

# 67. DATABASE FAILURE

If database write fails:

Do not pretend success.

Show:

**“లెక్క దాచలేకపోయాం. మళ్లీ ప్రయత్నించండి.”**

Preserve the user's entered information if possible.

---

# 68. CORRUPTED DATABASE

Application must have a recovery strategy.

At minimum:

* detect database initialization failure
* protect existing data
* offer backup/recovery path
* never automatically wipe database

The application must not depend on exact clock time for financial ordering.

Date is the primary user-facing grouping.

Timestamp is metadata.

---

# 159. SAME-DATE SORTING

Within a daily page:

Prefer logical category grouping:

1. Work notes
2. Income
3. Labour
4. Expenses
5. Summary

Within a category, newest entries can appear first or preserve creation order.

Do not create confusing mixed chronological lists.

---

# 160. ENTRY IDENTIFICATION

Every entry should visually show enough information to distinguish it.

Example:

**రవి — ₹800**

not merely:

**₹800**

Expense:

**టీ — ₹100**

not merely:

**₹100**

---

# 161. CONFIRMATION LANGUAGE

Keep confirmation questions short.

Bad:

**“Are you absolutely sure that you wish to permanently delete this financial transaction?”**

Good:

**“ఈ లెక్కను తీసేయాలా?”**

---

# 162. SUCCESS FEEDBACK

After saving:

Small:

**“దాచాం ✓”**

Do not interrupt the user with large dialogs.

---

# 163. ERROR FEEDBACK

Errors should:

* explain what happened
* say what to do next
* preserve input where possible

# 175. FINAL ACCEPTANCE CRITERION

The app is production-ready only when all three conditions are simultaneously true:

### Condition 1 — Technical

The application survives:

* offline usage
* crashes
* restarts
* migrations
* updates
* database changes
* large datasets
* interrupted downloads

without losing financial data.

### Condition 2 — Mathematical

Every total can be independently verified from the underlying entries.

### Condition 3 — Human

The actual father can use the core workflow without somebody standing beside him explaining the application.

If any one of these fails:

# DO NOT RELEASE.
